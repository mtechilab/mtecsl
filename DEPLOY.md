# Deploying the MTeC website (free hosting)

Status: **not yet deployed.** Nothing below is confirmed on a live site until the checklist in section 5 is completed.

## 1. Project facts (inspected)
- Static site generated by `python3 build.py` (Python 3.8+; tested on 3.12). Output folder: `dist/`.
- Dependency: Pillow, only used when `assets-src/hero.jpg` or `assets-src/campus.jpg` exist (`requirements.txt`).
- No server, database, API keys or secrets. The application system stays a separate backend (`https://mtec-payment-backend.onrender.com/apply`); the site only links to it.
- Environment variables (all optional): `SITE_URL` (canonical origin), `APPLY_URL` (backend form URL, default is production), `PYTHON_VERSION`.
- Clean URLs (`/about/` = `dist/about/index.html`), so no client-side routing rewrite is needed. `dist/404.html` is the not-found page. `dist/_headers` sets security and cache headers.

## 2. Recommended host: Cloudflare Pages (free)
Reasons: static assets are not bandwidth-metered, free HTTPS and custom domains, preview deployments per branch/PR, reads `_headers` and `404.html` as shipped, and no build-minute meter (500 builds/month cap instead).
Free-plan limits to know (verify on Cloudflare's "Pages > Limits" page): 500 builds/month, 1 concurrent build, 20-minute build timeout, 20,000 files per site, 25 MiB per file, 100 custom domains, 100 `_headers` rules. This site is about 150 files and well under 1 MB per page.
Alternatives: Netlify's free plan moved to credit-based limits in 2025 (bandwidth and builds draw from one monthly credit pool); Render static sites are fine but bandwidth allowances have changed between plans. Check current terms before choosing either.

## 3. Deploy steps
1. Create a GitHub repository; push this folder to `main`. Work on a branch: `git checkout -b feature/public-site`, open a pull request, review the diff and CI result (`.github/workflows/ci.yml` builds and runs the checks), then merge.
2. Cloudflare dashboard > Workers & Pages > Create > Pages > Connect to Git > pick the repository.
3. Build settings: framework preset **None**; build command `pip install -r requirements.txt && python3 build.py`; output directory `dist`; root directory blank; production branch `main`.
4. Environment variables (Production and Preview): `PYTHON_VERSION=3.12`. Leave `SITE_URL` empty for the first deploy.
5. Deploy. Note the address Cloudflare gives (`https://<project>.pages.dev`). HTTPS is automatic.
6. Set `SITE_URL` to that address (Settings > Environment variables) and redeploy. This turns on canonical URLs, the sitemap and social-image URLs.
7. Do not commit `dist/`, `.env` files or keys (`.gitignore` covers them). The repository contains no secrets.
8. If the dashboard offers Workers static assets instead of Pages, use the same build command and output directory, then re-test headers and the 404 page.

## 4. Backend and API base URL
The only backend reference is the Apply link. It comes from `APPLY_URL`, then `data/site.json` `apply_url`, then the production default, and is written into every link plus a `<meta name="apply-url">` tag used by `warmup.js`. Use `APPLY_URL` to point a preview deployment at a staging backend. Never put database credentials or payment keys in this repository.

## 5. Production test checklist (run on the live URL, then tick)
Desktop (Chrome and Firefox) and Android (Chrome and Samsung Internet if available, on mobile data):
- [ ] https:// loads with a valid certificate; http:// redirects to https.
- [ ] Open each route directly and refresh: `/`, `/about/`, `/programmes/`, `/programmes/computer-science/`, `/admissions/`, `/news/`, `/student-portal/`, `/contact/`.
- [ ] `/about` (no trailing slash) reaches the page; `/nope` shows the 404 page with HTTP status 404.
- [ ] Header menu (desktop) and Menu drawer (phone): every link works; Esc/Close works; active page is marked.
- [ ] Every "Apply" / "Student system" button opens the live `/apply` form. The form itself loads and a test submission is done by college staff only.
- [ ] Programmes search and category filter work; news empty state shows.
- [ ] Phone/email/map links open the dialer, mail app and Maps.
- [ ] `curl -I https://SITE/` shows `x-content-type-options`; `curl -I https://SITE/_a/<file>.css` shows `cache-control: ... immutable`.
- [ ] `/robots.txt`, `/sitemap.xml` (after SITE_URL is set), `/manifest.webmanifest`, `/favicon.ico` load.
- [ ] Airplane mode on a visited page shows the saved page; an unvisited page shows the offline page.
- [ ] Run PageSpeed Insights on the live home page and record the scores.
- [ ] Share a page link in WhatsApp/Facebook and confirm the preview image appears.

## 6. Rollback and recovery
- Bad release: Cloudflare Pages > Deployments > choose the last good production deployment > Rollback. Then fix in Git (`git revert <commit>`) and merge; the next build replaces it.
- Broken build: production keeps serving the last successful deployment; read the build log, fix on a branch.
- Service worker problem (users stuck on old pages): ship a `sw.js` that contains only `self.addEventListener('install',()=>self.skipWaiting());self.addEventListener('activate',e=>e.waitUntil(self.registration.unregister().then(()=>caches.keys()).then(k=>Promise.all(k.map(x=>caches.delete(x))))));` and redeploy. Browsers pick it up on their next visit.
- Total loss: the Git repository is the source of truth; `dist/` is rebuilt with `python3 build.py`. Keep a second maintainer on the GitHub and Cloudflare accounts and store account recovery codes safely.
- The backend is untouched by any website rollback.

## 7. Free-plan constraints in practice
Static pages have no cold starts or inactivity sleep. The separate Render backend may sleep when idle, so its first load can be slow (the site warns visitors and wakes it early). Builds use your 500/month allowance: avoid pushing many tiny commits to `main`. No serverless functions are used.

## 8. Connecting a custom domain later
1. Buy the domain (a registrar, or Cloudflare Registrar).
2. Pages project > Custom domains > Set up a domain; follow the DNS instructions. Cloudflare creates the certificate automatically. Apex domains (example.com) normally require the domain's DNS to be on Cloudflare; subdomains (www) can use a CNAME to `<project>.pages.dev`. Confirm in the dashboard prompts.
3. Change `SITE_URL` to the new address and redeploy; run `python3 tools/verify_seo.py dist https://NEW-ADDRESS` first.
4. Add a redirect from the old `pages.dev` address to the new domain (`_redirects` or a Cloudflare rule), submit the new sitemap in Search Console, update any links in the backend or social profiles, and set `SITE_URL` variable in GitHub (Settings > Variables) so CI checks the right origin.
